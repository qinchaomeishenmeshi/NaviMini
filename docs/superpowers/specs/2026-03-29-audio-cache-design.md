# NaviMini 整首歌曲缓存设计

## 目标

在不打断当前在线播放主链路的前提下，为 NaviMini 增加整首歌曲缓存能力：

- 第一次播放歌曲时，仍然使用远端流在线播放
- 播放开始后，在后台下载整首歌曲到本地缓存
- 后续再次播放同一首歌曲时，优先使用本地缓存文件

本次设计明确不做：

- 分片缓存
- 队列预下载
- 离线列表
- 离线模式切换
- 复杂自动修复和多级回退

## 背景与约束

当前项目的播放链路非常短：

- `PlaybackController` 负责播放状态与切歌
- `PlaybackQueueItemFactory` 直接把 `SubsonicClient.streamURL(...)` 生成的远端地址交给 `AVPlayerItem`
- 当前没有独立下载层、缓存索引层、文件生命周期管理

因此，如果直接把缓存逻辑塞进 `PlaybackController`，会明显破坏当前职责边界。

## 方案选择

### 方案 A：在 `PlaybackController` 内直接做缓存

优势：

- 接线最短
- 文件改动少

劣势：

- 播放控制器职责膨胀
- 下载、缓存命中、文件管理与播放状态耦合
- 后续最难维护

结论：不采用。

### 方案 B：新增独立缓存层，由播放链路消费结果

优势：

- 职责边界清晰
- 不破坏当前首次在线播放链路
- 可在不引入复杂离线系统的前提下增加缓存能力

劣势：

- 需要新增存储、下载、命中判定三个职责点
- 状态复杂度高于当前纯在线播放版本

结论：采用。

## 架构设计

新增独立缓存层，分为以下职责：

- `AudioCacheStore`
  - 管理缓存目录
  - 生成缓存键与文件路径
  - 判断本地缓存是否完整可用
  - 删除损坏缓存
- `AudioCacheDownloader`
  - 负责整首歌曲后台下载
  - 保证同一首歌不会重复并发下载
  - 下载完成后原子落盘
  - 下载失败只记日志，不影响当前在线播放
- `PlaybackQueueItemFactory`
  - 查询缓存命中情况
  - 命中时返回本地 `AVPlayerItem`
  - 未命中时返回远端 `AVPlayerItem`
  - 未命中时触发后台整首下载

## 数据流

1. 用户点歌。
2. `PlaybackController` 调用 `PlaybackQueueItemFactory.makeItem(...)`。
3. `PlaybackQueueItemFactory` 向 `AudioCacheStore` 查询当前歌曲 + 当前流格式是否已有完整缓存。
4. 若命中缓存：
   - 返回 `AVPlayerItem(url: fileURL)`。
5. 若未命中缓存：
   - 返回 `AVPlayerItem(url: remoteURL)`。
   - 同时让 `AudioCacheDownloader` 异步开始整首下载。
6. 下载完成后，文件写入 `Library/Caches/AudioCache/`。
7. 后续再次播放同一首歌时，优先命中本地缓存。

## 缓存目录与命名

缓存目录：

- `Library/Caches/AudioCache/`

命名原则：

- 不使用歌名、专辑名，避免文件名字符与重名问题
- 以 `song.id + formatKey` 作为稳定键

建议的缓存键组成：

- `song.id`
- 远端流格式

示例：

- `123_mp3_192.audio`
- `123_raw.audio`

扩展名不要求严格等于媒体原始扩展名，只要缓存层能稳定管理即可。

## 格式策略

缓存必须和实际播放格式绑定。

原因：

- 同一首歌可能因为 `raw` / `mp3(192)` / `flac` 形成不同文件内容
- 若缓存键不含格式，后续可能出现“命中错格式缓存”的错误

因此缓存键必须包含流格式信息。

## 完整缓存判定

本次只做工程上的整首缓存，不做复杂媒体完整性校验。

判定条件：

- 下载任务成功结束
- 临时文件成功移动到目标路径
- 文件大小大于 0

如果响应头里存在 `Content-Length`，则额外记录并用于基本校验；没有时不阻塞缓存成功。

## 错误处理

### 下载失败

- 不影响当前在线播放
- 记录 `MetricsLogger`
- 不弹复杂错误恢复 UI

### 命中损坏缓存

- 删除损坏文件
- 本次回退远端在线播放
- 重新触发一次后台整首下载

这里的回退仅限单次缓存命中失败，不引入复杂自动修复状态机。

## 并发规则

只缓存“实际播放过的歌曲”，不预下载整个队列。

同一首歌在同一格式下：

- 若已有下载任务在进行中，不重复发起第二个任务
- 若本地已有完整缓存，不重复下载

## 测试要求

至少覆盖以下回归点：

- 缓存键生成稳定且包含格式
- 命中完整缓存时返回本地 URL
- 未命中缓存时返回远端 URL
- 未命中时会触发后台下载
- 同一首歌不会重复并发下载
- 损坏缓存会删除并回退远端

## 风险评估

### 优势

- 不打断首次在线播放体验
- 缓存能力可独立演进
- 后续重复播放时可提升稳定性与速度

### 劣势

- 项目状态复杂度上升
- 磁盘占用会持续增长，后续需要清理策略
- 服务端内容变化时，本地缓存可能过期，本次设计不主动校验版本
- 一旦缓存层实现不严谨，容易引入“文件存在但不可播”的边界问题

## 结论

本次实现应坚持以下边界：

- 保留当前在线播放主链路
- 只新增“播放后整首缓存、下次优先本地”的能力
- 不把缓存逻辑扩展成完整离线系统
- 不把下载管理塞进 `PlaybackController` 或 `SubsonicClient`
